# opencode-postgres-readonly

[English](README.md) · **Русский**

Read-only PostgreSQL инструменты для OpenCode: ограниченные `SELECT`-запросы,
метаданные схемы и список проектов/окружений для доверенных баз данных.

## Возможности

- **`database_exec`** — выполнение ограниченного read-only SQL-запроса к PostgreSQL.
- **`database_schema`** — метаданные таблиц/столбцов `public`, без произвольного SQL и строк данных (до 1 000 столбцов).
- **`database_list`** — список database-проектов и их окружений.

Инструменты полностью автономны: не используют общий код и не зависят от
внешних файлов учётных данных. Вся конфигурация хранится локально в
`config.json` рядом с исходными файлами.

## Установка

Скопируйте содержимое репозитория в каталог инструментов OpenCode:

```bash
# Создайте каталог инструментов, если его нет
mkdir -p ~/.config/opencode/tools/opencode-postgres-readonly

# Скопируйте исходные файлы и шаблон конфигурации (без локального config.json)
cp -r database.ts config.ts config.example.json db requirements.txt \
  ~/.config/opencode/tools/opencode-postgres-readonly/
```

Установите обе Python-зависимости в каталоге установки (Python 3.10+):

```bash
cd ~/.config/opencode/tools/opencode-postgres-readonly
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Инструмент использует соседний `.venv/bin/python`, если он есть, иначе `python3`. В окружении запуска должны быть доступны Bun и API плагинов OpenCode. Для отдельного checkout устанавливайте JS-зависимости из собственного `package.json`, никогда не из каталога без локального манифеста.

### Создание локальной конфигурации

Скопируйте шаблон в `config.json` в каталоге установки и заполните реальными
данными:

```bash
cd ~/.config/opencode/tools/opencode-postgres-readonly
cp config.example.json config.json
chmod 600 config.json
```

### Перезапуск OpenCode

После установки завершите текущую сессию OpenCode и запустите её снова
(`opencode`), чтобы новые инструменты подхватились.

## Конфигурация

`config.json` намеренно игнорируется Git. Структура:

```json
{
  "projects": {
    "example-db": {
      "dev": {
        "driver": "postgres",
        "host": "db.example.invalid",
        "port": 5432,
        "database": "exampledb",
        "sslmode": "prefer",
        "auth": {
          "user": "reader",
          "password": "replace_with_real_password"
        }
      }
    }
  }
}
```

| Поле | Обязательное | Описание |
|------|:-----------:|----------|
| `driver` | да | Тип БД (пока только `postgres`) |
| `host` | да | Хост базы данных |
| `port` | да | Порт |
| `database` | да | Имя базы данных |
| `sslmode` | да | Режим SSL: `prefer`, `require`, `disable`, `verify-full` |
| `auth.user` | да | Пользователь БД |
| `auth.password` | да | Пароль |

Вложенность: `projects.<project>.<environment>`. У одного проекта может быть
несколько окружений (`dev`, `staging`, `prod`). Если `environment` не указан,
используется первое окружение из списка. Конфигурация читается один раз и
кэшируется в памяти на время жизни процесса.

> **Важно:** `config.json` не коммитится (в `.gitignore`). Права доступа —
> `chmod 600`.

## Использование

### database_exec

Выполняет read-only SQL-запрос:

```
database_exec({ project: "example-db", environment: "dev", query: "SELECT id, name FROM products LIMIT 5" })
```

Аргументы:

| Аргумент | Обязательный | Описание |
|----------|:-----------:|----------|
| `project` | да | Имя проекта из `config.json` |
| `environment` | нет | Имя окружения; по умолчанию — первое |
| `query` | да | Один read-only SQL-запрос |

Успешный ответ:

```json
{
  "columns": ["id", "name"],
  "rows": [[1, "Товар А"], [2, "Товар Б"]],
  "row_count": 2,
  "truncated": false
}
```

Ошибки:

```json
{"error": "Query execution failed", "reason": "..."}
{"error": "Unexpected error", "reason": "An unexpected internal error occurred"}
```

### database_list

Список проектов и окружений:

```
database_list()
```

Ответ:

```json
{
  "example-db": ["dev", "prod"]
}
```

## Безопасность и ограничения

- Проверка PostgreSQL AST через `pglast`: один SELECT, включая нерекурсивные читающие CTE. Неизвестные конструкции отклоняются; запрещены EXPLAIN, запись, управление транзакциями, SELECT INTO и блокировка строк.
- Явная схема таблицы — только `public`; системные отношения `pg_*` запрещены. Чтение метаданных выполняется отдельным фиксированным запросом.
- Функции и типы — только из разрешённого списка встроенных, с квалификацией `pg_catalog`. Явное указание пользовательской схемы оператора запрещено.
- Серверная транзакция READ ONLY, откат при завершении, `search_path=pg_catalog,public`.
- Максимум 1 000 строк и 1 МиБ сериализованного JSON; `truncated` обозначает усечение. Серверный курсор не загружает весь результат сразу.
- Подключение: 5 секунд; SQL: 10 секунд на серверную команду, включая отдельный fetch курсора; ожидание блокировки: 1 секунда. Общий дедлайн Python-процесса из TypeScript — 25 секунд.
- Максимальная длина входного SQL — 10 000 символов. Ошибки БД и аварийное завершение процесса маскируются.
- Обе зависимости из `requirements.txt` должны быть установлены в Python-окружение инструмента.

Это не песочница для недоверенной схемы БД: представления, RLS, пользовательские типы столбцов, перегруженные операторы и неявные преобразования могут косвенно запускать код. Используйте минимально привилегированную роль и ограничьте исполнение функций; агент не должен иметь доступ к учётным данным, изменению инструмента или альтернативному клиенту БД. Одно огромное значение может занять память до усечения ответа. READ ONLY не отменяет внешние побочные эффекты.

### Граница доверия

Инструмент обеспечивает ограниченное чтение доверенной схемы БД, а не гарантирует отсутствие побочных эффектов произвольного кода внутри БД. Проверяется присланный SQL, но не каждая функция, скрытая за объектами базы. READ ONLY блокирует обычную запись в текущей транзакции даже при наличии прав записи у учётки, но не защищает другие соединения, файлы или внешние сервисы.

- Представления и политики доступа к строкам (RLS) могут косвенно вызывать функции. Пользовательские типы, операторы и неявные преобразования также могут запускать код БД.
- Для production используйте отдельную минимально привилегированную учётку, не суперпользователя. Агент не должен читать учётные данные, менять инструмент или обходить его другим клиентом БД.
- Это не механизм маскирования данных или разграничения доступа: доступные чувствительные строки возвращаются по запросу. Лимиты действуют на один вызов; повторные вызовы позволяют прочитать больше данных.
- Таймауты и ограничения выдачи снижают ресурсные риски, но не задают строгую квоту CPU, диска БД или памяти процесса. Одно большое значение может быть выделено в памяти до усечения. Дедлайн 25 секунд завершает локальный процесс; немедленная отмена произвольной внешней работы не гарантируется.
- Поддержка SQL намеренно неполная. Рекурсивные CTE, EXPLAIN, произвольные функции, явно указанные пользовательские типы/операторы и неподдерживаемые AST-конструкции отклоняются. Списки разрешённых встроенных функций и типов находятся в `db/exec.py`.

### Проведённые проверки

**Локальные автоматические проверки:** прошли 11 Python unit-тестов, ESLint, Ruff, проверка типов TypeScript и `git diff --check`. Тесты покрывают допустимый SQL, запрещённые конструкции, валидацию до подключения, лимиты строк/байтов, очистку соединений и чтение схемы; взаимодействие с БД в этих тестах заменено моками.

**Живой интеграционный прогон:** прошли 23 проверки на PostgreSQL 16.13 в Docker под суперпользователем, в отдельной одноразовой БД. Проверены SELECT, CTE/JOIN/агрегация, результаты date/numeric/UUID, пустая выдача, метаданные схемы, усечение до 1 000 строк и лимит 1 МиБ. Таймауты SQL и блокировки наблюдались примерно через 10 и 1 секунду. Тестовые данные остались неизменными после всех проверок атак; одноразовая БД удалена.

Проверенные категории атак:

- Прямые DELETE, DROP и TRUNCATE.
- Инъекция нескольких команд через идентификаторы с долларом и выход из транзакции.
- Модифицирующий данные CTE.
- Обход фильтра через quoted-функцию/комментарий и изменение настроек транзакции.
- Обход запрета системных каталогов через Unicode-идентификаторы.
- Вызов функции записи через другое соединение.
- Прямой вызов прикладной функции.
- Блокировка строк, SELECT INTO и EXPLAIN ANALYZE.
- Косвенная запись через представление: заблокирована PostgreSQL READ ONLY.

Живой прогон проверял Python-исполнитель, а не полный путь OpenCode → TypeScript. Прямые атакующие вызовы отклонялись до исполнения; это не доказывает безопасность всех функций расширений. Дедлайн TypeScript 25 секунд, таймаут подключения при сетевом сбое, побочные эффекты RLS/типов/операторов, внешние эффекты и другие версии PostgreSQL интеграционно не проверялись. Одноразовый интеграционный сценарий не включён в репозиторий; `bun run test` запускает только unit-тесты. Результаты подтверждают проверенные сценарии, но не являются сертификацией безопасности.

### Проверки для разработки

Запускать из корня этого репозитория, где находится собственный `package.json`:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
bun install --frozen-lockfile
bun run lint
bun run typecheck
bun run test
```

`typecheck` проверяет только TypeScript. Не добавляйте в коммиты `config.json`, виртуальные окружения, каталоги зависимостей и локальные тестовые данные; публикуйте исходники и lock-файлы, а не архив всей директории.

## Разрешения в opencode.jsonc

Минимальный фрагмент для разрешения инструментов:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permission": {
    "database_schema": "allow",
    "database_exec": "allow",
    "database_list": "allow"
  }
}
```

Для агента со строгими правами (`"*": "deny"`):

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "agent": {
    "db-reader": {
      "mode": "subagent",
      "description": "Read-only database access.",
      "permission": {
        "*": "deny",
        "database_schema": "allow",
        "database_exec": "allow",
        "database_list": "allow"
      }
    }
  }
}
```
